# 结构化检索 MVP 技术方案

## 1. 整体流程

两阶段流水线：**索引阶段**（一次性，文档 → 字段库）和**查询阶段**（多次，问题 → 答案）。

```
索引阶段：招标文件.docx/.pdf/.txt
              │
              ▼
       [文本解析 + 章节切分]
              │
              ▼
   ┌──────────────────────┐
   │  规则提取（先尝试）    │
   │  - 16个字段逐一匹配     │
   └──────────────────────┘
              │
       命中？──否──┐
        │是          │
        ▼            ▼
   置信度=高      [LLM兜底提取]
   人工确认=否     - 仅对规则未命中的字段调用
        │          - 要求LLM返回：字段值/来源章节/来源原文
        │          - 置信度=中，人工确认=否
        │                │
        └────────┬───────┘
                 ▼
         [字段库 JSON 落盘]
         fields.json（16条记录）


查询阶段：用户问题（自然语言）
              │
              ▼
       [问题 -> 字段映射]
       - 关键词/同义词匹配，命中1个或多个字段
              │
              ▼
       [从字段库读取记录]
              │
              ▼
       [格式化输出：答案/来源章节/来源原文/置信度]
```

## 2. 模块划分

| 模块 | 职责 | 输入 | 输出 |
|---|---|---|---|
| `schema.py` | 定义16个字段的元信息：字段名、规则提取用的正则模式、查询匹配用的关键词/同义词 | - | 字段定义表（常量） |
| `doc_parser.py` | 把 docx/pdf/txt 转成带章节标记的纯文本，识别"第X章""一、""（一）"等章节锚点 | 原始文件路径 | `[{章节标题, 文本内容, 起止位置}]` 的章节列表 |
| `rule_extractor.py` | 对每个字段尝试正则/关键词规则匹配，在章节列表中定位 | 章节列表 + 字段定义 | 命中的字段记录（含来源章节、来源原文），未命中字段名列表 |
| `llm_extractor.py` | 对规则未命中的字段，调用大模型，prompt 中明确要求"如果原文中没有该信息，必须明确说明未找到，禁止编造"，并要求返回 JSON 格式的字段值+来源章节+来源原文 | 未命中字段列表 + 全文（或相关章节） | 补全的字段记录 |
| `field_store.py` | 字段库的读写，JSON 文件持久化，每条记录包含 schema 中的6个属性 | 字段记录 | `fields.json` |
| `query_router.py` | 把用户自然语言问题映射到1个或多个字段（支持"基本信息"这种聚合查询，映射到多个字段） | 用户问题字符串 | 命中的字段名列表 |
| `answer_formatter.py` | 按照需求里的示例格式拼装输出 | 字段记录 | 格式化文本 |
| `build_index.py` | 索引阶段的入口脚本，串联 parser → rule_extractor → llm_extractor → field_store | 文件路径 | 落盘的 `fields.json` |
| `query.py` | 查询阶段的入口脚本，串联 query_router → field_store → answer_formatter | 字段库路径 + 问题 | 终端打印答案 |

## 3. 字段库数据结构

每个字段一条记录，存成 JSON：

```json
{
  "field_name": "项目编号",
  "field_value": "CF25ZFF0142",
  "source_section": "第一章 招标公告 / 一、项目基本情况",
  "source_text": "（一）项目编号：CF25ZFF0142",
  "confidence": "高",
  "human_confirmed": false,
  "extraction_method": "rule"
}
```

- `confidence` 取值：高（规则命中）/ 中（LLM抽取）/ 低（LLM明确表示未找到或不确定）
- `extraction_method` 额外记录是 `rule` 还是 `llm`，方便后续调试和迭代规则库，需求文档本身没要求这个字段，但实现上建议保留
- 若字段在文档中确实不存在，记录 `field_value: null`，`confidence: 低`，避免查询时静默失败

## 4. 规则提取设计

规则提取本质是"锚点词 + 正则"组合，例如：

- **项目编号**：锚点词「项目编号」「编号」，紧跟的正则 `[:：]\s*([A-Za-z0-9\-]+)`
- **最高限价**：锚点词「最高限价」「最高投标限价」，正则匹配金额（数字+万元/元/人民币符号）
- **是否接受联合体**：锚点词「联合体」，在其附近窗口内匹配「不接受/不允许」vs「接受/允许」，做布尔判断
- **开标时间/投标截止时间**：锚点词 + 日期时间正则 `\d{4}年\d{1,2}月\d{1,2}日.*?\d{1,2}[:：]\d{2}`

每个字段的规则配置在 `schema.py` 里声明为数据（锚点词列表 + 正则模板 + 章节优先级），不写在代码逻辑里，方便后续迭代而不动逻辑。

**规则命中的判定标准**：锚点词在某章节命中，且紧邻文本能被正则成功捕获 → 记为命中，置信度"高"。若锚点词命中但正则没捕获到值（比如格式异常），算"未命中"，交给 LLM。

## 5. LLM 兜底提取设计

- **触发条件**：仅针对规则未命中的字段，不会对已经规则命中的字段重复调用（省 token，且规则结果更可信）
- **输入范围**：优先把"项目基本情况"相关章节喂给 LLM，而不是整篇文档，减少幻觉空间和 token 消耗；如果该章节都没有，才退到全文
- **Prompt 关键约束**：
  - 必须返回 JSON，字段为 `field_value`、`source_section`、`source_text`
  - 明确要求 `source_text` 必须是文档中逐字存在的原文片段（不是转述），便于事后做字符串校验（校验 `source_text` 是否真的是原文的子串，如果不是则降级为低置信度，防止幻觉）
  - 找不到时必须返回 `field_value: null`，禁止编造
- **后处理校验**：拿到 LLM 返回后，用 `source_text in 原文` 做一次字符串包含校验，校验失败则把该字段标记为"低置信度+建议人工确认"，而不是直接相信 LLM

## 6. 查询路由设计（问题 → 字段映射）

需求里列的查询问题分两类：

1. **单字段查询**：如"项目编号是多少" → 直接映射到「项目编号」一个字段
2. **聚合查询**：如"基本信息是什么" → 映射到一组字段（项目编号、项目名称、招标方式、招标人、采购单位），按需求示例里"基本信息"的常见构成预先定义这个聚合分组

匹配方式：每个字段在 `schema.py` 里维护一组同义词/触发关键词（如「招标人」字段对应关键词「招标人」「招标单位」），问题先去除"是什么/是多少/有哪些"等问句后缀，再做关键词包含匹配。聚合分组（如"基本信息""联系方式"）作为特殊的虚拟字段，命中后展开成多个真实字段依次输出。

匹配不到任何字段时，明确提示"该问题不在结构化检索范围内，建议转向量检索"，呼应需求里第6节的边界。

## 7. 输出格式

严格复用需求里给的示例格式，单字段查询输出一条，聚合查询依次输出多条，每条都带完整的四要素（答案/来源章节/来源原文/置信度）。

## 8. MVP 范围内不做的事

- 不做多文档管理（一次只处理一个标书）
- 不做章节切分的复杂版面还原（如表格内字段），留作已知局限，先支持纯文本段落里的字段
- 不做人工确认的交互界面，`human_confirmed` 字段先固定为 `false`，留好字段位置，方便后续接审核流程
