# 语义检索技术方案

## 一、模块定位

语义检索用于处理招标文件中的长文本理解类问题：

```
用户用自然语言提问
→ 系统找到招标文件中语义相关的原文片段
→ 大模型基于原文片段生成可溯源的答案
```

适合问题示例：

```
标包2的数据治理平台有哪些功能？
路侧智能感知系统要建设哪些内容？
用户需求书的总体要求是什么？
这个项目的技术建设重点是什么？
```

不适合问题示例（应使用结构化检索）：

```
项目编号是多少？
最高限价是多少？
投标截止时间是什么？
```

## 三、整体数据流

```
招标文件.md
    │
    ▼ chunker.py
    章节识别 → 切块（每块含标题）
    │
    ├──► SQLite (rag.db)       存 chunk 元数据和原文
    ├──► chunks.index          FAISS 向量索引
    └──► chunks_map.json       FAISS 位置 → chunk_id 映射

用户提问
    │
    ▼ 问题向量化
    ▼ FAISS 召回 Top10
    ▼ chunks_map.json 得到 chunk_id
    ▼ SQLite 查原文和章节路径
    ▼ LLM 生成答案
    │
    输出：答案 + 来源章节
```

## 四、切块方案

### 4.1 核心原则

- 标题是重要信息，每个 chunk 必须携带所在章节的标题
- chunk 不跨章节边界
- content 为空也产生 chunk，保留标题信息

### 4.2 章节识别

按 `#` 标题树识别章节，构建 `section_path`：

```
# 第二章 用户需求书
## 总体要求
### 标包2

→ section_path = "第二章 用户需求书 / 总体要求 / 标包2"
```

维护一个层级栈，遇到新标题时弹出同级及以下，压入当前标题，拼接路径。

### 4.3 切块流程

```
对每个章节：

├─ content 为空
│       产生 1 个 chunk
│       chunk_text  = section_path + "\n" + title
│       source_text = title
│
└─ content 不为空
        按空行切段落
        列表块（连续 -/* 行）整体为一个段落
        表格块（连续 | 行）整体为一个段落
        │
        逐段累加（字数不含标题头）：
        │
        ├─ 累计 ≤ 800字 → 继续加段落
        │
        ├─ 加入下一段后 > 800字
        │       输出当前 chunk
        │       从该段落重新开始新 chunk
        │       各 chunk 之间无 overlap
        │
        └─ 某段落本身 > 800字 → 句子级分块
                按 。？！ 切句，逐句累加
                超过 800字 → 输出子块，从下一句重新开始
                每个子块补充前后上下文：
                  前缀 = 上一子块尾部 100字，延伸到句首（上一个。？！之后）
                  后缀 = 下一子块开头 100字，延伸到句尾（最近的。？！）

每个 chunk 的 chunk_text 固定格式：
    section_path + "\n" + title + "\n" + [前缀] + 核心内容 + [后缀]

source_text = 核心内容（干净原文，用于展示）
```

### 4.4 chunk 元数据

| 字段 | 说明 |
|---|---|
| `chunk_id` | uuid4() 唯一标识 |
| `document_id` | 来源文件名（不含路径和扩展名） |
| `section_path` | 章节路径，用于溯源 |
| `chunk_text` | 用于 embedding（含标题和前后上下文） |
| `source_text` | 干净原文，用于展示 |
| `chunk_type` | 按 section_path 关键词判定 |
| `package_no` | 从 section_path 提取标包编号 |
| `created_at` | 入库时间 |

`chunk_type` 判定规则（按优先级）：

| section_path 含 | chunk_type |
|---|---|
| 技术要求 | technical_requirement |
| 用户需求 | requirement |
| 评分 | scoring |
| 合同 | contract |
| 资格 | qualification |
| 开标 / 投标 | submission |
| 其余 | other |

`package_no` 提取规则：

```python
re.search(r"标包\s*(\d+)", section_path)
```

## 五、FAISS 与 SQLite 对应关系

FAISS 和 SQLite 通过 `chunks_map.json` 解耦，不依赖 rowid。

```
入库时：
  按向量化顺序记录 chunk_id 列表 → 保存为 chunks_map.json

查询时：
  FAISS 返回行号 N
  → chunks_map.json[N] 得到 chunk_id
  → SELECT * FROM chunks WHERE chunk_id = ?
```

三个文件必须同一次入库生成，重建索引时一起重建：

```
chunks.index       FAISS 向量索引
chunks_map.json    [chunk_id, chunk_id, ...]  位置与 FAISS 一一对应
rag.db             SQLite，按 chunk_id 查询原文和元数据
```

## 六、入库（build_index.py）

**用法：**

```bash
uv run build_index.py <招标文件.md>
```

**流程：**

```
1. 调用 chunk_document() 获取 chunk 列表，打印切块统计
2. 初始化 SQLite（rag.db），建 chunks 表，清除同 document_id 旧数据
3. 按顺序写入 chunk 到 SQLite
4. 按同样顺序取 chunk_text，批量调用 DashScope 向量化
5. 构建 FAISS IndexFlatIP（L2归一化 → 余弦相似度）
6. 保存 chunks.index 和 chunks_map.json
```

**SQLite 表结构：**

```sql
CREATE TABLE IF NOT EXISTS chunks (
    chunk_id     TEXT PRIMARY KEY,
    document_id  TEXT,
    section_path TEXT,
    chunk_text   TEXT,
    source_text  TEXT,
    chunk_type   TEXT,
    package_no   TEXT,
    created_at   TEXT
);
```

**向量化配置：**

```
API    = DashScope text-embedding-v4
维度   = 1024
批次   = 10条/次
失败   = 重试1次，间隔3s
限速   = 批次间 sleep 0.1s
```

## 七、检索（query.py）

**用法：**

```bash
uv run query.py <招标文件.md>
```

**流程：**

```
1. 根据文件名确定 document_id
2. 加载 chunks.index（FAISS）和 chunks_map.json
3. 连接 rag.db（SQLite）
4. 交互式循环，用户输入问题
5. 问题向量化（text-embedding-v4）
6. FAISS 召回 Top10，返回行号列表
7. chunks_map.json[行号] 得到 chunk_id
8. SQLite 查询 source_text、section_path
9. 拼装 Prompt → qwen-plus 生成答案
10. 打印答案 + 来源章节
```

**Prompt 结构：**

```
你是招标文件分析助手。严格基于以下原文片段回答，不得脱离原文。
若片段中无相关信息，回答"未找到相关内容"。

[片段1] 来源：第二章 用户需求书 / 技术要求 / 标包2
……原文……

[片段2] 来源：……
……原文……

问题：{question}

给出答案，末尾列出引用的来源章节。
```

**输出格式：**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━
问题：xxx

答案：
……

来源章节：
  · 第二章 / 技术要求 / 标包2
  · 第二章 / 总体要求
━━━━━━━━━━━━━━━━━━━━━━━━━━
```
