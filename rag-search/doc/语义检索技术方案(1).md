# 语义检索技术方案

## 1. 模块定位

语义检索用于处理招标文件中的长文本理解类问题，适合查询技术要求、建设内容、服务要求、功能模块、方案重点等内容。

它解决的是：

```text
用户不是精确搜索某个词，而是用自然语言表达问题；
系统根据语义相似度，找到招标文件中意思相关的原文片段。
```

例如：

```text
标包2的数据治理平台有哪些功能？
用户需求书主要要求是什么？
路侧智能感知系统要建设哪些内容？
自动驾驶公交平台有哪些功能模块？
这个项目的技术建设重点是什么？
```

---

## 2. 适用范围

语义检索适合以下场景：

| 场景 | 示例问题 |
|---|---|
| 技术需求查询 | 数据治理平台有哪些功能？ |
| 标包内容查询 | 标包3主要建设什么？ |
| 用户需求总结 | 用户需求书的重点是什么？ |
| 方案生成前置查询 | 写技术方案需要关注哪些要求？ |
| 相似语义查询 | 数据共享、接口服务、数据资产相关内容有哪些？ |

不适合单独处理：

```text
项目编号是多少？
最高限价是多少？
投标截止时间是什么？
有哪些★条款？
有哪些无效投标风险？
```

这些问题应优先使用结构化检索或关键词检索。

---

## 3. 总体流程

```text
Markdown 招标文件
→ 文档清洗
→ 章节识别
→ 表格处理
→ 文本切块
→ Chunk 元数据标注
→ Embedding 向量化
→ 写入向量库
→ 用户提问
→ 问题向量化
→ 相似度召回
→ 元数据过滤
→ 结果重排
→ 返回原文片段
→ 大模型基于证据生成答案
```

---

## 4. 文本切块方案

语义检索效果主要取决于切块质量。

### 4.1 按章节优先切块

招标文件应优先按章节结构切分，而不是简单按固定字数切分。

示例：

```text
第二章 用户需求书 / 总体要求
第二章 用户需求书 / 技术要求 / 标包1
第二章 用户需求书 / 技术要求 / 标包2
第二章 用户需求书 / 技术要求 / 标包3
```

### 4.2 表格转自然语言

招标文件中的技术要求大量存在于表格中，需要将表格转换为可检索的自然语言文本。

示例：

```text
标包2：大数据共享与治理系统平台。
功能模块：数据资源管理。
子功能模块：数据建模。
详细功能：支持 SQL、向导模式等多种方式建模……
```

这样用户搜索“数据治理平台有哪些功能”时，可以准确命中相关内容。

### 4.3 Chunk 大小建议

第一版建议：

```text
每个 chunk：500-1000 中文字
重叠 overlap：100-150 字
表格行可按“标包 + 功能模块 + 子功能 + 详细功能”组织
每个 chunk 保留章节路径和标包信息
```

---

## 5. Chunk 元数据设计

每个 chunk 至少保存以下信息：

```text
chunk_id
document_id
section_path
chunk_text
source_text
chunk_type
package_no
package_name
start_pos
end_pos
created_at
```

推荐 chunk_type：

```text
basic_info
qualification
submission
requirement
technical_requirement
table
contract
scoring
risk
other
```

其中：

```text
section_path：用于答案溯源
package_no：用于标包过滤
chunk_type：用于查询范围控制
source_text：用于展示原文依据
```

---

## 6. 向量库方案

原型阶段建议：

```text
Chroma
```

产品化阶段建议：

```text
Qdrant / Milvus / Elasticsearch Vector
```

向量库存储内容：

```text
embedding
chunk_id
document_id
section_path
chunk_type
package_no
package_name
chunk_text
```

结构化元数据可同时保存到 SQLite 或 PostgreSQL，方便过滤和展示。

---

## 7. Embedding 模型选择

中文招标文件建议使用中文或多语言 Embedding 模型。

可选模型：

```text
bge-m3
bge-large-zh
text-embedding-3-small
text-embedding-3-large
```

原型阶段推荐：

```text
bge-m3 或 bge-large-zh
```

选择原则：

```text
中文语义效果好
支持较长文本
成本可控
可本地部署
```

---

## 8. 查询处理流程

以用户问题为例：

```text
标包2的数据治理平台有哪些功能？
```

处理流程：

```text
1. 识别查询对象：标包2
2. 识别查询主题：数据治理平台、功能
3. 将问题转换为向量
4. 在向量库中召回 Top K 相似 chunk
5. 使用元数据过滤 section_path 和 package_no
6. 对候选 chunk 进行重排
7. 返回最相关的原文片段
8. 大模型基于片段生成答案
```

---

## 9. 检索策略

推荐采用：

```text
向量检索 + 元数据过滤 + 结果重排
```

### 9.1 向量检索

根据问题语义召回相关片段。

适合：

```text
数据治理有哪些功能？
智能感知系统建设内容是什么？
响应式公交平台有哪些模块？
```

### 9.2 元数据过滤

根据章节、标包、chunk 类型缩小范围。

示例：

```text
只检索第二章 用户需求书
只检索技术要求
只检索标包2
只检索 table 类型 chunk
```

### 9.3 结果重排

召回后根据多种因素重新排序：

```text
向量相似度
章节匹配度
标包匹配度
关键词覆盖度
chunk_type 权重
```

---

## 10. 返回结果要求

语义检索的返回结果必须可溯源。

推荐格式：

```text
回答：
……

来源：
第二章 用户需求书 / 技术要求 / 标包2

依据片段：
……
```

返回内容包括：

```text
答案
来源章节
原文片段
相关度
chunk_id
```

大模型只能基于召回片段回答，不能脱离原文自由发挥。

---

## 11. 与其他检索方式的关系

| 检索方式 | 适合问题 | 示例 |
|---|---|---|
| 结构化检索 | 固定字段 | 项目编号、最高限价、开标时间 |
| 关键词检索 | 明确词语和风险 | 无效投标、★、保证金、盖章 |
| 语义检索 | 长文本理解 | 技术要求、建设内容、功能模块 |
| 混合检索 | 综合问题 | 生成响应矩阵、总结用户需求 |

推荐使用顺序：

```text
固定字段问题 → 结构化检索
风险合规问题 → 关键词检索
技术需求问题 → 语义检索
复杂综合问题 → 混合检索
```

## 12. 最小可用方案

第一版可以按以下方式实现：

```text
输入：Markdown 招标文件
切块：按章节和表格语义切块
存储：SQLite 保存 chunk 元数据，Chroma 保存向量
模型：bge-m3 或 bge-large-zh
检索：Top 5-10 相似片段
输出：答案 + 来源章节 + 原文片段
```

最小验收问题：

```text
标包1要建设哪些功能？
标包2的数据治理平台有哪些功能？
路侧智能感知系统有哪些建设内容？
用户需求书总体要求是什么？
这个项目的技术建设重点是什么？
```

## 13. 风险与注意事项

### 13.1 切块过大

问题：

```text
召回内容不精准，答案容易混杂。
```

建议：

```text
按章节和表格语义切块，控制 chunk 大小。
```

### 13.2 切块过小

问题：

```text
上下文不足，大模型无法完整总结。
```

建议：

```text
设置合理 overlap，并保留章节上下文。
```

### 13.3 表格未处理

问题：

```text
技术要求表格无法被准确检索。
```

建议：

```text
将表格转成自然语言描述后再向量化。
```

### 13.4 缺少元数据

问题：

```text
无法按标包、章节、类型过滤。
```

建议：

```text
每个 chunk 必须保存 section_path、package_no、chunk_type。
```

---

## 14. 一句话总结

语义检索的技术方案是：

```text
将招标文件按章节和表格语义切成片段，
用 Embedding 模型转成向量并写入向量库，
用户提问时召回语义相关片段，
再结合章节、标包、关键词进行过滤和重排，
最终基于原文片段生成可溯源答案。
```
