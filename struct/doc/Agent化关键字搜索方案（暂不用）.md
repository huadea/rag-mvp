# Agent 化关键字搜索方案

> **状态：暂不用。** 本文只做方案存档，供后续需要时参考，当前不实施、不改动代码。

---

## 1. 背景

`struct/` 现有架构是一条固定流水线：

```
schema.py（预定义字段 + 锚点词/同义词）
   ↓
rule_extractor.py（正则/锚点扫描，命中即取值或收集候选）
   ↓
llm_extractor.py（规则未命中的字段，单独装填上下文，调用一次 LLM 兜底）
```

这几周迭代过程中反复出现同一类问题：**文档的实际措辞、结构跟预先写好的锚点/正则对不上**（如"投标文件递交截止时间"在原文写成"递交投标文件截止时间"、时间和地点分成两个独立段落、"招标控制价"全文根本没有这个字面词只在表格"合计"行给数字）。每次都是发现一个新的不匹配案例，就手工加一个锚点变体或写一个专用解析函数，属于"打补丁"式维护，长期不可持续。

由此讨论了一个替代思路：参考 Claude Code 自身搜索代码/文档的方式——不预先固定锚点和流程，而是让模型自己决定搜什么、要不要再搜、什么时候下结论。

---

## 2. Claude Code 的搜索方式 vs 现有 struct/ 架构

Claude Code（智能体）搜索信息时，不是"候选收集"和"LLM 判断"两个独立阶段，而是模型自己在**同一条连续推理流**里决定下一步：

```
每一轮：模型看到当前完整上下文（任务描述 + 之前所有工具调用结果）
        → 生成下一步动作（可能是一次工具调用，也可能是最终答案）
工具调用结果被塞回上下文，进入下一轮，直到模型自己给出结论
```

没有外部代码在"编排"这个过程——"该不该继续搜""这个候选对不对"，都是模型基于训练学到的判断力当场生成出来的，不是一套 if/else 规则或打分公式。

对照表：

| | struct/ 现状 | Claude Code 方式 |
|---|---|---|
| 是否有固定 schema | 有——20 个字段的锚点词/同义词表 | 没有，任务描述里临时确定要找什么 |
| 候选收集 | 独立的程序化步骤（正则扫描） | 模型自己决定搜索词，自己调工具 |
| 判断/裁决 | 独立的一次 LLM 调用 | 和搜索决策在同一推理流里，没有阶段划分 |
| 调用次数 | 每字段最多 1 次（规则未命中才调用） | 不固定，模型自己决定要搜几轮 |
| 可预测性/成本 | 高/低，适合无人值守批处理 | 低/高，适合有人监督的一次性探索任务 |

## 3. 改造方案设计（如果要做）

只对"规则+同义词经常打不中、又没有清晰结构可写专用解析器"的字段做 agent 化（如"招标人/采购人""评标方法"这类表述多样、位置不固定的字段），其余字段维持现状：

```
1. 把"正则扫描全文档"包装成模型可调用的工具（search_keyword），
   而不是程序直接调用的函数——模型自己决定搜什么词、要不要再搜
2. 新增"多轮循环调度器"：对每个字段起一个独立的多轮对话 session，
   反复"模型决策 → 执行工具 → 结果喂回 → 模型再决策"，
   直到模型给出最终答案或达到轮次上限
3. system prompt 从"一次性问答"重写为"工具使用 + 终止条件"指令
4. 确认 DeepSeek API 的 function/tool calling 支持程度和实际表现
   （OpenAI 兼容接口通常支持，但"模型能不能稳定按预期调用工具、
   稳定判断终止"需要用真实文档实测，不能假设）
5. 新增轮次/成本熔断机制，防止模型在某个字段上无限搜索
6. 新增可观测性：需要能追踪"某字段走了几轮、每轮搜了什么词、
   模型怎么一步步收敛的"，调试复杂度比现在高不少
```

结构化表格字段（标段/包号划分、投标保证金、招标控制价）和布尔字段（联合体、分包）**不纳入 agent 化范围**——这些数据本身有固定格式，现有的精确正则/表格解析已经是最优解，agent 化只会增加不确定性和成本，没有收益。

---

## 4. 工作量评估

- 只对 1～2 个"疑难字段"试点：**小到中等**，其余代码不动，风险可控
- 全部字段都 agent 化：**大**，相当于把 `llm_extractor.py` 推倒重写，还要处理多字段并发跑多轮会话的调度、成本、超时问题

不是加几个函数就能完成，是新增一种运行模型：现有代码是"遍历字段列表，每个字段跑一次函数"，agent 化后是"每个字段是一个独立的、有状态的多轮会话"，两者在代码结构上是不同的骨架。

---

## 5. 效果预期（分字段类型）

| 字段类型 | Agent 化收益 |
|---|---|
| 结构化表格字段 | 没有收益，反而更差——精确解析已是最优解 |
| 布尔字段 | 基本没收益——判断逻辑本来就简单固定 |
| 措辞不可预测的字段 | 收益明显——本质上是"没法预先枚举所有变体"，恰好是规则的死穴、agent 的强项 |

即"整体切换成 agent 方式"不是应该无差别套用的决定，收益集中在特定一小类字段上。

---

## 6. 成本/延迟

现有架构：一个字段最多 1 次 API 调用。Agent 化后：一个字段可能要 2～5 轮才能收敛，且轮次随文档措辞难易浮动，不再是固定成本。一份文档如果有 10 个字段需要 agent 介入，调用次数可能从个位数涨到 20～50 次，处理时间和费用明显上升，且变得不可预测。

---

## 7. 结论

**暂不实施。** 原因：

1. 收益集中在少数"措辞不可预测"的字段上，不构成"全面重构"的理由
2. 成本/延迟/可预测性代价明显，且需要先验证 DeepSeek 的 tool-calling 实际表现，这部分目前没有实测数据
3. 现有架构（规则 + 同义锚点 + 单轮 LLM 兜底）经过这几周迭代，已经能覆盖 20 个字段中的绝大部分，边际收益不足以覆盖改造成本

如果未来要重新评估，建议路径：

1. 先挑 1～2 个反复出问题的字段（如"招标人/采购人"）做 agent 化原型
2. 验证 DeepSeek 的 function-calling 能否稳定工作、实际轮次和成本是多少
3. 用几份不同的真实标书跑对比（agent 版本 vs 现有版本），看召回率提升是否值这个成本
4. 有实测数据支撑后，再决定是否扩大范围
